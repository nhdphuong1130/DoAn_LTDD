# Knowledge Graph Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the reviewed, versioned, locally embedded Neo4j projection that later tutor, quiz, and remediation phases can safely consume.

**Architecture:** SQL Server remains authoritative for concepts, assertions, and graph-build state. A deterministic builder reads one verified SQL projection, embeds fragments and concepts with a configured FastEmbed model, writes a build-scoped Neo4j graph and indexes, validates it, then activates it without modifying the previous active build. Runtime retrieval is not switched in this phase.

**Tech Stack:** Python 3.12, SQLAlchemy 2, Alembic, SQL Server, Neo4j 5.26 Community, Neo4j Python driver 5.28, FastEmbed 0.8, Pydantic Settings, pytest, Docker Compose

**Spec:** `docs/plans/2026-09-20-evidence-first-adaptive-knowledge-graph-design.md`

## Global Constraints

- SQL Server is the source of truth; Neo4j is a rebuildable projection.
- Only verified, published source fragments and verified assertions may enter an activatable graph.
- Concepts are independent of units; unit placement is represented by relationships.
- Every semantic assertion retains provenance, confidence, review status, creator/model metadata, and reviewer metadata.
- Indexing and query-time embedding configurations must have the same model, version, prefixes, preprocessing version, and dimensions.
- Graph nodes are scoped by `build_id`; an incomplete or failed build must never replace the active build.
- Integration tests must use isolated infrastructure and must never write to the runtime Neo4j or SQL Server databases.
- All Cypher values are parameterized; the only interpolated identifiers are validated build labels and index names generated by application code.
- Existing public tutor and quiz behavior remains unchanged during Phase 1.

## Review Focus

- **Mixed embedding dimensions:** Task 3 tests reject any generated vector whose dimension differs from configuration.
- **Unverified evidence or assertions:** Task 2 and Task 4 tests prove they are excluded from a graph projection.
- **Partial build failure:** Task 6 tests prove failure records `FAILED` while the previous build remains `ACTIVE`.
- **Cross-version contamination:** Task 5 tests prove vector indexes and graph queries are bound to exactly one `build_id`.
- **Runtime database contamination by tests:** Task 7 runs integration tests in a disposable Compose project and verifies cleanup.

- [ ] **Step 4: Implement importer policy**

```python
class OntologyImporter:
    def import_manifest(self, manifest: OntologyManifest) -> OntologyImportResult:
        evidence_ids = manifest.verified_evidence_fragment_ids()
        if evidence_ids != self._repository.verified_fragment_ids(evidence_ids):
            raise ApplicationError(
                "ontology_evidence_not_verified",
                "Verified ontology assertions require verified textbook evidence",
                422,
            )
        manifest.validate()
        return self._repository.apply_ontology(manifest)
```

The SQL repository performs one transaction, stores concepts and assertions,
and records an `AuditEvent` containing manifest ID, checksum, ontology version,
and counts. Re-importing the same manifest is a no-op. A changed payload with an
already-used manifest ID is rejected as `ontology_manifest_conflict`.

- [ ] **Step 2: Create disposable Compose topology**

`compose.integration.yaml` defines `sqlserver-integration`,
`neo4j-integration`, and a `knowledge-tests` container on a project-local
network. Do not mount named runtime volumes or publish host ports. The test
container receives only integration credentials and service hostnames.

- [ ] **Step 3: Add cleanup-safe runner**

```bash
#!/usr/bin/env bash
set -euo pipefail
project="english7-knowledge-integration"
cleanup() {
  docker compose -p "$project" -f compose.integration.yaml down -v --remove-orphans
}
trap cleanup EXIT
docker compose -p "$project" -f compose.integration.yaml up \
  --build --abort-on-container-exit --exit-code-from knowledge-tests
```

The script uses a fixed narrow project name and exact compose file; it does not
remove any container or volume outside that project.
